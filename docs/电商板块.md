# superMall 电商板块（mall）

> 独立可部署服务，与外卖板块（`superMall-takeout`）**并存且互不影响**。
> 最后更新：2026-09-21（**P0~P5 + P7 完成 + 商品详情缓存三防（P8 提前），P6 营销暂缓**）
>
> 📖 **接口契约单独成文**：[`电商接口文档.md`](电商接口文档.md)（91 个端点、字段表、错误码一览、前端对接速查）。
> 本文只讲**架构与设计决策**。

---

## 0. 一句话

外卖（点餐 + 骑手配送）与电商（商品 + 物流）是**两条互斥的履约链路**。
与其把外卖重构成电商，不如**把电商做成独立服务**：外卖代码一行不动，电商从零起一个干净的模块，
两边靠"表前缀 / Redis 前缀 / MQ 前缀 / 端口"物理隔开，需要共享的只有**用户账号**和**收货地址**。

## 1. 架构与隔离

```
                    ┌──────────────────────────────┐
                    │  MySQL（同一实例、同一个库）   │
                    │  ├─ 外卖表：orders/product/…  │
                    │  ├─ 电商表：mall_*（新）       │
                    │  └─ 共享表：sys_user / address │
                    └──────────────────────────────┘
                              ▲            ▲
        ┌─────────────────────┘            └─────────────────────┐
        │                                                        │
┌───────────────────────┐                            ┌───────────────────────┐
│ superMall-takeout      │                            │ superMall-mall        │
│ 外卖服务  :8080        │                            │ 电商服务  :8081        │
│ · 用户/商家/骑手 三端   │                            │ · 买家 /api/mall/user  │
│ · 备餐 + 抢单 + 配送    │                            │ · 运营 /api/mall/admin │
│ 【代码零改动】          │                            │ · 目录 /api/mall/catalog│
└───────────────────────┘                            └───────────────────────┘
        │                                                        │
        └──────────────┬─────────────────────────────────────────┘
                       ▼
            同一个 Redis（key 前缀不同）
            同一个 OSS bucket（目录不同）
```

### 隔离矩阵

| 资源 | 外卖 | 电商 | 手段 |
| --- | --- | --- | --- |
| 进程 / 端口 | 8080 | **8081** | 独立 Spring Boot 应用 |
| Java 包 | `com.supermall.*` | `com.supermall.mall.*` | 包名分区 |
| 数据表 | `orders` `product` `sku`… | `mall_order` `mall_product` `mall_sku`… | **表名前缀** |
| Redis key | `stock:sku:{id}` | `mall:stock:sku:{id}` | **前缀** |
| MQ | `order.exchange` | `mall.order.exchange`（P4 才加） | **命名空间** |
| OSS 目录 | `supermall/products/` | `supermall/mall/` | 目录 |
| 日志文件 | `logs/supermall.log` | `logs/mall.log` | 文件名分开 |
| WebSocket | `/ws/{token}` | （暂无） | 路径 |
| JWT（买家） | 头 `token` | **同一个头、同一把密钥** | ✅ **故意共享** |
| JWT（其他角色） | `merchant-token` / `delivery-token` | `mall-admin-token` | 各自独立 |

### ⚠️ 三条红线（违反会出线上事故）

1. **表名绝不能与外卖那 12 张表重名** —— 电商一律 `mall_` 前缀
2. **Redis key 绝不能与外卖重名** —— 尤其 `stock:*`，重名会**库存串号**；电商一律 `mall:` 前缀
3. **MQ 命名绝不能与外卖重名** —— 重名会让两个服务**抢同一条消息**；电商一律 `mall.` 前缀

`MallApplicationTests.redisKeysAreNamespaced` 已把第 2 条做成断言，防止以后新增 key 忘加前缀。

## 2. 共享的东西（有意为之，不是遗漏）

| 共享项 | 说明 | 为什么 |
| --- | --- | --- |
| `sys_user` 表 | 商城买家就是外卖用户，**一个账号两边通用** | 用户体验；且不用动现有表结构 |
| `address` 表 | 收货地址共用；P3 已加一个**可空**列 `area_code`（电商读写，外卖不碰） | 同上；加可空列对外卖零影响 |
| `superMall-common` 模块（**唯一共享库**） | `Result` / `JwtUtil` / `AliOssUtil` / `JacksonObjectMapper` / `BaseContext` / 邮箱密码校验注解，以及 `User` 实体、`UserLoginDTO`/`UserRegisterDTO`/`UserLoginVO`、`@EmailAccount`/`@StrongPassword`、`CaptchaAware` | 横切能力 + 账号体系本来就是同一套，所以合并为一个共享模块 |
| user JWT 密钥 | 电商签发买家 token 时用**外卖同一把密钥** | 所以**外卖登录的 token 在电商也能用**，反之亦然 |

### 有意复制的东西（不是为了 DRY，是为了解耦）

| 复制项 | 原因 |
| --- | --- |
| `MallCaptchaImageUtil`（画验证码） | 原类在 `superMall-takeout` 里，让电商依赖外卖的启动模块会把两个板块耦合成"一个挂了另一个起不来" |
| `MallCaptchaService` + `MallCaptchaAspect` + `@RequireCaptcha` | 同上；且电商的 Redis key 前缀不同 |
| `MallTraceIdInterceptor`、`MallGlobalExceptionHandler`、`MallRedisScriptConfig`、`MallOssConfiguration` | 同上 |

> 取舍：重复 8 个小文件，换来**外卖服务零改动 + 两个板块可独立部署、独立回滚**。值得。

## 3. 启动

### 依赖

沿用外卖那套中间件，**不需要新增任何组件**：

| 组件 | 地址 | 说明 |
| --- | --- | --- |
| MySQL | `localhost:3306` | 与外卖同库 |
| Redis | `localhost:6379` | 与外卖同实例（**版本 5.0.14，别用 `GETDEL` 等 6.2+ 命令**） |
| OSS | 同外卖 bucket | 目录 `supermall/mall/` |
| `JASYPT_ENCRYPTOR_PASSWORD` | 环境变量 | **必需**，与外卖同一个主密码 |

### 建表（幂等，可重复执行）

```bash
mysql --ssl-mode=DISABLED --default-character-set=utf8mb4 -uroot -p supermall < sql/mall.sql
```

包含 P0（`mall_admin`）+ P1（品牌 / 分类 / SPU / 多图 / 规格 / 规格值 / SKU / SKU关联）
+ P2（推荐位 / 收藏 / 足迹）+ 种子数据 + 排序用索引。

### 启动

```bash
# ① 外卖服务（8080）—— 与电商完全无关，也可以只起它
java -jar superMall-takeout/target/superMall-takeout-0.0.1-SNAPSHOT.jar

# ② 电商服务（8081）
java -jar superMall-mall/target/superMall-mall-0.0.1-SNAPSHOT.jar
```

看到 `Started MallApplication` 即成功。两个服务可以任意单独启停。

### 4.2 P1：商品体系

**数据模型（8 张表）**

```
mall_brand          品牌
mall_category       分类（parent_id + level，最多 3 级）
mall_product        SPU（price_low/price_high/stock 是由 SKU 派生的冗余字段）
mall_product_image  多图
mall_spec           规格项（颜色 / 尺码）
mall_spec_value     规格值（白 / 黑 / M / L）
mall_sku            SKU（规格组合）
mall_sku_spec       SKU ↔ 规格值 关联
```

**两个关键设计决定**

| 决定 | 说明 |
| --- | --- |
| **不做"无规格"特例** | 无规格商品 = 1 个**不关联任何规格值**的 SKU。购物车/下单/库存永远只有一套逻辑。<br>（外卖那边 `product.stock` 与 `sku.stock` 双轨，导致了"无规格商品 `skuId` 要传 0"这个坑） |
| **价格/库存由 SKU 派生** | `mall_product.price_low / price_high / stock` 由服务端在保存时重算（`refreshAggregates`），<br>列表页只读 SPU 就能显示价格区间与库存，不用 JOIN `mall_sku` |

**接口**

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/mall/admin/categories/tree` | 分类树（含禁用的，后台编辑用） |
| POST/PUT | `/api/mall/admin/categories` | 新增 / 修改（父分类层级 +1，最多 3 级；**不支持改父分类**） |
| DELETE | `/api/mall/admin/categories/{id}` | 删除（有子分类或有商品时拒绝） |
| GET | `/api/mall/admin/brands` | 品牌列表（名称模糊 + 状态过滤） |
| POST/PUT/DELETE | `/api/mall/admin/brands` | 品牌增删改（同名拒绝、被商品引用则不可删） |
| GET | `/api/mall/admin/products/page` | 商品分页（**传父分类会展开成其后代分类**） |
| GET | `/api/mall/admin/products/{id}` | 商品详情（多图 + 规格项 + SKU 列表） |
| POST/PUT | `/api/mall/admin/products` | 新增 / 修改（SPU + 多图 + 规格 + SKU **一次提交**） |
| PUT | `/api/mall/admin/products/{id}/status?status=1\|0` | 上下架 |
| DELETE | `/api/mall/admin/products/{id}` | 删除（**上架中的不允许删**；连带清理多图/规格/SKU） |
| POST | `/api/mall/admin/file/upload` | 上传单张图到 OSS，返回 URL |
| POST | `/api/mall/admin/file/upload-batch` | 批量上传（最多 10 张），返回 URL 列表 |
| GET | `/api/mall/catalog/categories` | **公开**：分类树（只含启用的） |
| GET | `/api/mall/catalog/brands` | **公开**：品牌列表 |
| GET | `/api/mall/catalog/products/page` | **公开**：在售商品分页（强制 `status=1`） |
| GET | `/api/mall/catalog/products/{id}` | **公开**：商品详情 |

**保存商品的请求体形态**（新增/修改共用）

```json
{
  "categoryId": 4,
  "brandId": 1,
  "name": "纯棉圆领T恤",
  "subtitle": "260g 重磅纯棉",
  "detail": "100% 精梳棉…",
  "images": ["https://.../a.png", "https://.../b.png"],
  "specs": [
    { "name": "颜色", "values": ["白", "黑"] },
    { "name": "尺码", "values": ["M", "L"] }
  ],
  "skus": [
    { "skuCode": "TS-W-M", "price": 79, "stock": 100, "specValues": ["白", "M"] },
    { "skuCode": "TS-W-L", "price": 79, "stock": 120, "specValues": ["白", "L"] },
    { "skuCode": "TS-B-M", "price": 82, "stock": 90,  "specValues": ["黑", "M"] },
    { "skuCode": "TS-B-L", "price": 82, "stock": 80,  "specValues": ["黑", "L"] }
  ]
}
```

> **SKU 用「规格值字符串」而不是 id 引用**：新增商品时规格/规格值/SKU 是同一次请求创建的，
> 前端此时拿不到库里的 id。`specValues` 按 `specs` 顺序一一对应，服务端解析成 id。
> 详情接口也按同样的字符串结构返回 —— 所以运营后台的编辑表单可以
> 「GET 详情 → 改 → PUT 原样提交」，不用做 id ↔ 值 的来回映射。

**服务端强制的校验**（都实测拦截）

| 场景 | 结果 |
| --- | --- |
| SKU 数 ≠ 各规格值数量的乘积 | 拒绝，提示「应为 N 个，实际 M 个」 |
| SKU 的 `specValues` 个数 ≠ 规格项数 | 拒绝 |
| 规格值不在该规格的定义里 | 拒绝并指出是哪个值 |
| 规格组合重复 | 拒绝 |
| 无规格商品给了多个 SKU | 拒绝 |
| 无规格商品却带 `specValues` | 拒绝 |
| 规格项 > 3 / 规格名重复 / 规格值重复 / 规格无值 | 拒绝 |
| 商品挂在非叶子分类 / 分类已禁用 | 拒绝 |
| 一个 SKU 都没有 | 拒绝 |

### 4.3 P2：浏览与发现

**数据模型（3 张表）**

```
mall_banner     首页推荐位 / 轮播图（position + sort + 生效时间窗 start/end）
mall_favorite   收藏夹（唯一键 user_id + product_id）
mall_footprint  浏览足迹（唯一键 user_id + product_id，重复浏览累加 visitCount）
```

**索引**：给 `mall_product` 加了 4 个「`status` + 排序字段」组合索引
（`sales` / `rating` / `price_low` / `create_time`），支撑前台排序不产生 filesort。

> 加索引用的是**幂等的存储过程**（MySQL 不支持 `ADD INDEX IF NOT EXISTS`），
> 所以 `sql/mall.sql` 可以反复执行。

**接口**（19 个，契约见 [`电商接口文档.md`](电商接口文档.md)）

| 分组 | 数量 | 覆盖 |
| --- | --- | --- |
| 公开目录扩展 | 6 | 推荐位、推荐商品、分类树（带商品数）、品牌、商品搜索、商品详情 |
| 买家 | 9 | 收藏 5 + 足迹 4 |
| 运营后台 | 6 | 推荐位 CRUD + 上下线 |

**四个关键设计决定**

| 决定 | 说明 |
| --- | --- |
| **排序只认白名单** | `orderBy` 由服务层归一化（非法值静默回落 `default`），XML 里用 `<choose>` 展开成固定 SQL 片段 —— **不用 `${}` 拼字符串**，从根上避免注入 |
| **价格区间用「有交集」语义** | `priceHigh >= min AND priceLow <= max`，即「该商品有 SKU 落在这个价位」。比「最低价落在区间内」更符合直觉 |
| **收藏 / 足迹不过滤下架商品** | 下架了也要能看到并标灰（`status=0`），否则用户会觉得收藏"凭空消失" |
| **足迹走 UPSERT 去重** | 唯一键 + `ON DUPLICATE KEY UPDATE` 累加 `visitCount`；同一商品永远只有一行，不会把足迹刷成噪音 |

另外两个细节：

- **分类导航带商品数**：`productCount` 是「含所有后代分类」的在售商品总数，
  服务层后序遍历累加（一次聚合查询 + 内存累加，不做递归 SQL，不依赖 MySQL 8+ 的 CTE）
- **收藏用 `INSERT IGNORE`**：靠唯一键天然幂等。不用「先查再插」—— 并发下两边都查到"没收藏"就会撞唯一键报错

### 4.4 P3：购物车与地址

**数据模型（1 张新表 + 共享表加 1 列）**

```
mall_cart_item   购物车明细（user_id + sku_id 唯一；自营无商家维度）
address          共享表，新增可空列 area_code（省市区末级编码）
```

> **不建 `mall_area` 表**：省市区是静态区划（3800+ 条），放在
> `superMall-mall/src/main/resources/mall-area.json`，由 `MallAreaServiceImpl`
> 启动时一次性加载进内存。零查询、零 IO，前端逐级 `parentCode` 查询即可。

**接口**（14 个 + 1 个公开区划）

| 分组 | 数量 | 覆盖 |
| --- | --- | --- |
| 公开目录扩展 | 1 | 省市区三级联动 `/catalog/areas` |
| 买家 - 购物车 | 8 | 列表+汇总、角标、加购、改数量、单行勾选、全选、删单行、清空/清理失效 |
| 买家 - 地址 | 6 | 列表、详情、新增、修改、删除、设默认 |

**购物车的三个关键设计决定**

| 决定 | 说明 |
| --- | --- |
| **不存价格快照** | 购物车只存 `product_id + sku_id + number`，列表每次 JOIN `mall_sku` 取当前价。<br>满足「价格实时计算」；结算金额永远与下单时一致。（外卖存快照，是另一种取舍） |
| **自营不需要购物车头表** | 外卖按「用户 × 商家」分车，电商不引入商家概念，一张明细表 + `(user_id, sku_id)` 唯一键就够。<br>加购粒度是 **SKU**：79 元的 M 码与 82 元的 L 码在购物车里是两行。 |
| **失效商品不物理删** | 商品下架 / SKU 失效 / 售罄 / 库存不足的行照常返回，带 `valid=false` + `invalidReason`，<br>但**不计入结算金额、不能被选中**（对外 `selected` 恒为 0），并提供 `scope=invalid` 一键清理。 |

**两个并发/幂等细节**

- **加购用一条原子 SQL**：`INSERT ... ON DUPLICATE KEY UPDATE number = LEAST(number + VALUES(number), stock)`。
  并发加购同一 SKU 不会插出两行，也不会把数量加到超过库存（超了静默截断并返回最终值）。
- **全选只勾有效行**：`UPDATE ... JOIN mall_sku JOIN mall_product ... WHERE p.status=1 AND s.status=1 AND s.stock>0`。
  一击全绝不能把失效商品带进结算。

**地址的三个约定**

| 约定 | 说明 |
| --- | --- |
| **区划名称由服务端回填** | 前端三级联动只传末级 `areaCode`，服务端校验它是叶子节点后写入 `province / city / district`。<br>名称不会写错，也不会出现「code 是北京的、名称是上海的」这类脏数据。也兼容直接传三个名称（外卖老地址）。 |
| **默认地址互斥** | 第一条自动默认；设默认先 `clearDefault` 再 `setDefault`；编辑默认地址不传 `isDefault` 也不会被顺手取消。 |
| **共用 `address` 表** | 外卖建的地址在电商可见、可设为默认；电商新增的地址带 `area_code`，外卖侧读写零影响。 |

### 4.5 P4：订单履约

**数据模型（4 张新表）**

```
mall_order       订单（状态机 + 金额 + 收货快照 + expire_time）
mall_order_item  订单明细（商品/规格/价格快照）
mall_shipment    物流单（一单一张：公司 + 单号）
mall_refund      退货退款申请（previous_status 用于驳回回退）
```

**接口**（16 个）

| 分组 | 数量 | 覆盖 |
| --- | --- | --- |
| 买家 - 订单 | 8 | 下单令牌、提交、分页、详情、取消、确认收货、申请退款、退款进度 |
| 买家 - 支付 | 2 | 支付令牌、支付（Mock） |
| 后台 - 订单 | 3 | 分页、详情、发货 |
| 后台 - 退款 | 3 | 分页、详情、审核 |

**状态机**

```
PENDING_PAYMENT ─支付─► PENDING_DELIVERY ─发货─► PENDING_RECEIPT ─收货─► COMPLETED
       │                                                                      │
       └─取消/超时─► CANCELLED                    可退款状态─申请─► REFUNDING ─┬─同意─► REFUNDED
                                                                                 └─驳回─► 回退
```

**五个关键设计决定**

| 决定 | 说明 |
| --- | --- |
| **所有流转用条件更新** | `where status = 期望值`，并发重复流转只会成功一次，天然幂等（取消/发货/收货/退款申请/退款审核都是） |
| **金额服务端算** | `total - discount + freight = pay`；前端只能决定「用哪个地址、买购物车里哪些行」，传不了价格 |
| **快照保证历史可读** | 明细与收货信息都是下单时快照：商品改名改价下架、地址改删，都不影响历史订单 |
| **防超卖两层** | Redis + Lua 预扣（挡并发）+ DB `stock >= number` 条件扣减（最终一致）；取消/退款/超时都回补两层 |
| **退款单不建 order_id 唯一键** | 并发互斥靠「订单状态 → REFUNDING」的条件更新；驳回后订单回退，允许重新申请 |

**两个幂等细节**

- **下单**：Redis 令牌（Lua 检查+删除）+ 唯一索引 `(user_id, submit_token)` 双重兜底；
- **支付**：Redis 令牌一次性消费 + `markPaidIfPending` 条件更新；只有真正流转成功的那次才累加销量。

**销售口径**：支付成功时 `mall_sku.sales` 与 `mall_product.sales` 同时 +N；退款通过时 -N（`greatest(...,0)` 兑底不为负）。

### 4.6 P5：评价系统

**数据模型（2 张新表 + 商品 2 个派生列）**

```
mall_review        评价（一个 order_item 只能评一次；追评是同一行的追加）
mall_review_image  评价图（type：1 初评 / 2 追评）
mall_product       + review_count（评价数）+ good_rate（好评率%，rating>=4）
```

**接口**（8 个）

| 分组 | 数量 | 覆盖 |
| --- | --- | --- |
| 买家 | 4 | 批量评价、追评、我的评价、订单评价情况 |
| 公开 | 2 | 商品评价分页（按星级/有图）、评价统计 |
| 后台 | 2 | 评价分页、删除违规评价 |

**四个关键设计决定**

| 决定 | 说明 |
| --- | --- |
| **评价粒度 = 订单明细** | 一个 `order_item` 只能评一次（唯一键），所以“哪件商品还没评”天然可判定，不会重复 |
| **只有已完成订单能评** | 服务端校验 `order.status = COMPLETED`；“订单评价情况”接口告诉前端每件是否已评 |
| **追评是同一行的追加** | `follow_content` / `follow_time`，条件更新（`follow_time is null`）防重复；**追评不改评分**，无需重算商品聚合 |
| **聚合写时重算** | 新增/删除评价后 `refreshReviewAggregates(productId)`：`rating=AVG`、`review_count=COUNT`、`good_rate=rating>=4 占比`；无评价时回落到 5.00 / 0 / 100.00 |

**匿名与显示昵称**

- 查询用 `coalesce(u.nickname, u.username)` 取昵称；`anonymous=1` 一律返回「匿名用户」；
- 实名但无昵称时，邮箱打码为 `u***@qq.com`，不泄露完整邮箱。

**评价图片**：初评图与追评图用同一张表的 `type` 区分，接口分别返回 `images` 与 `followImages`。

### 4.7 P7：运营后台（会员 + 统计）

> 商品管理（P1）、订单管理 / 退款审核（P4）已在前面的阶段交付，P7 补齐**会员管理**与**销售看板**。

**接口**（7 个，不新建表）

| 分组 | 数量 | 覆盖 |
| --- | --- | --- |
| 会员 | 3 | 分页、详情（含统计）、启用/禁用 |
| 统计 | 4 | 看板总览、销售趋势（日/月）、品类占比、热销 TOP N |

**三个设计要点**

| 要点 | 说明 |
| --- | --- |
| **成交口径统一** | 所有统计只算 `pay_status = 'PAID'` 的订单；未支付、已退款（REFUNDED）均不计入 |
| **趋势补 0 在服务层** | SQL 只 `GROUP BY` 有成交的分组；服务层生成完整日期序列并补 0，前端折线不断档（不建日期维表） |
| **品类按顶级分类归并** | 商品可挂在 3 级分类，SQL 向上 `left join` 最多 3 层得到根分类（不用递归 CTE） |

**会员管理**：会员就是买家（共享 `sys_user`），列表带订单数 / 消费额 / 评价数（子查询实时算）。
唯一写操作是改 `status`（启用/禁用）—— 禁用后同账号在外卖与电商都无法登录。
为避免破坏买家侧「只查/只插」的约定，单独建了 `MallMemberMapper`。

### 4.8 P8 提前：商品详情缓存三防

> 需求进阶项原文就是「Redis 缓存热点商品 + 分布式锁或 Lua 脚本实现秒杀限流」，
> 这里先把前半句做掉，实现方式**与外卖 `ProductServiceImpl.getDetail` 同款**。

**不新增表、不改接口形态**，只加一个缓存工具类 + 一段 Cache-Aside 逻辑：

```
GET /api/mall/catalog/products/{id}   （公开目录，吃缓存）
GET /api/mall/admin/products/{id}     （运营后台，直查 DB —— 改完立刻看到改动）

读  ① getJson(mall:product:detail:{id}) 命中 → 返回
    ② isNullMarked → 直接判「商品不存在」（不打 DB）              防穿透（空值缓存 60s）
    ③ tryLock(key,10s) 抢到才回源；抢不到 sleep 50ms 重试读缓存   防击穿（setnx + 双重检查）
    ④ 写缓存 TTL = 300 + [0,120) 秒随机抖动                     防雪崩
写  保存 / 上下架 / 删除商品 → 删 mall:product:detail:{id}        Cache-Aside
```

| 文件 | 作用 |
| --- | --- |
| `utils/MallRedisCacheClient` | Cache-Aside 工具：`setJson`（抖动 TTL）/ `setNull` / `getJson` / `delete` / `isNullMarked` / `tryLock` / `unlock` |
| `scripts/mall_unlock.lua` | 释放锁：值匹配才删，防误删别人的锁 |
| `MallProductServiceImpl.detailCached` / `evictCache` | 三道防线 + 写操作删缓存 |

**与外卖的差异（有意）**：

| 点 | 外卖 | 电商 |
| --- | --- | --- |
| 缓存入口 | 公开 `getDetail` 直接带缓存 | 拆成 `detail()`（不缓存，后台用）/ `detailCached()`（缓存，公开用），因为两者共用同一个 `detail()` |
| key | `product:detail:{id}` + `cache:lock:` | `mall:product:detail:{id}` + `mall:cache:lock:`（三条红线：绝不重名） |
| 缓存工具类 | `takeout/utils/RedisCacheClient` | `mall/utils/MallRedisCacheClient`（**有意复制**，两个板块必须能各自独立部署） |

**取舍**：TTL 内 `stock / sales / rating / reviewCount` 可能是旧值（最长 ~7 分钟）——
加购/下单都以 DB 为准，评分展示走**不缓存**的 `/review-stats`，所以只影响展示层的最终一致。

## 8. 已知限制

| # | 事项 | 说明 |
| --- | --- | --- |
| 1 | 电商与外卖**共用同一个数据库** | 逻辑隔离而非物理隔离；要物理隔离需改 `application-dev.yml` 的 `database` 并自建买家表 |
| 2 | 电商的买家登录是**独立实现**（读同一张表） | 好处是不依赖外卖服务运行；代价是登录逻辑有两份 |
| 3 | `address` 已加可空列 `area_code` | 电商侧写入省市区末级编码；外卖侧不读写它，零影响 |
| 4 | Redis 5.0.14 | 不要用 `GETDEL`/`SINTERCARD` 等 6.2+ 命令；验证码已用 Lua 实现原子取值+删除 |
| 5 | 电商日志写 `logs/mall.log` | 与外卖的 `logs/supermall.log` 分开，避免 Windows 下抢同一个文件 |
| 6 | **不支持移动分类** | 改父分类要连带重算整棵子树的 level，还会引入"挂到自己后代下"的环。P1 明确拒绝而不是留脏数据 |
| 7 | 商品保存是**整体覆盖** | 多图/规格/SKU 走「先删后建」；SKU 的 `sales` 会按 `skuCode` 尽量带过来（无规格单 SKU 直接沿用），匹配不上则置 0 |
| 8 | 修改商品时**想清空字段要传空字符串** | `mall_product` 的 update 是全量更新（不做 `<if>` 条件拼接），传 `null` 会被写成 null，「不传」与「清空」由前端用 `""` 区分 |
| 9 | 演示商品**没有配图** | P1 交付的是多图上传**能力**（已实测真传 OSS）；种子商品的 `main_image` 为 NULL，前端必须占位 |
| 10 | SKU 库存**已进 Redis** | Lua 预扣 + 启动预热；保存商品后按新 SKU id 重新同步（`syncProductSkuStock`） |
| 11 | 商品 `rating` / `goodRate` 由评价真实聚合 | P5 已实现：新增/删除评价后重算；无评价时 rating=5.00、goodRate=100.00，前端用 `reviewCount===0` 判「暂无评价」 |
| 12 | 商品 `sales` 在**支付成功时累加**，退款通过时扣回 | P2 的「销量排序」现在有真实数据了 |
| 13 | **搜索是 MySQL LIKE**（商品名 / 副标题 / 品牌名 / 分类名） | ES + 高亮 + 拼音是 P8 进阶项，届时替换 SQL 即可，**对外接口形态不变** |
| 14 | **浏览足迹每次详情页访问都写一次库** | 同一商品是 UPSERT 累加（不新增行），但仍是写操作；量大了应改成 Redis 缓冲后批量落库 |
| 15 | 收藏 / 足迹**不过滤下架商品** | 有意为之：下架了也要能看到并标灰（`status=0`），否则用户会觉得收藏"凭空消失" |
| 16 | 改推荐位时**无法把生效时间窗置空** | `MallBannerMapper.update` 用的是 `<if != null>`，传 `null` 等于不改。需要清空时间窗时先删后建 |
| 17 | **购物车加购会被库存截断** | 累加超过库存时截到库存上限并返回最终数量，而不是报错；前端用返回的 `number` 更新角标 |
| 18 | **省市区是静态数据** | 从 npm `china-area-data` 生成（34 省 / 375 市 / 3397 区县），存在 `resources/mall-area.json`；<br>行政区划调整时需重新生成。港澳的末级是「市」一级，`district` 会为空 |
| 19 | **地址上限 20 条** | 超过返回「最多只能保存 20 条收货地址」 |
| 20 | **电商不接 MQ** | 超时关单只用定时任务（需求就这么要求）；外卖那边是 MQ 延迟队列 + 定时任务双保险 |
| 21 | **退款是整单退款** | 金额 = 订单实付；不支持单件部分退款（P5+ 可扩展） |
| 22 | **退款没有凭证图** | P4 只收原因 + 文字说明；晒图是 P5 评价系统的能力 |
| 23 | **退款审核「同意」即回补库存 + 扣回销量** | 不区分「仅退款」（货不要了）与「退货退款」（货退回）—— 两者都回补，演示够用 |
| 24 | **超时关单靠 `expire_time`** | 下单时写 `now + pay-timeout-minutes`；定时任务每分钟扫一次（最坏晚 1 分钟） |
| 25 | **支付是 Mock** | 无真实支付网关；`MallPaymentService` 是唯一需要换的实现（P8 接支付宝沙箱） |
| 26 | **评价只能评价一次 + 追评一次** | 粒度是订单明细（唯一键）；追评不改评分，所以不重算聚合 |
| 27 | **好评率口径 = 4 星及以上** | 存在 `mall_product.good_rate`；星级分布不存，实时 GROUP BY（数据量小） |
| 28 | **评价图片不校验存在性** | 只存 URL 字符串（晒图走 OSS 上传）；演示阶段不调 HEAD 验活 |
| 29 | **删评价是硬删除** | 后台删除后不可恢复，并立即重算商品聚合（无「隐藏/软删」状态） |
| 30 | **会员统计靠子查询实时算** | 单页 ≤ 100 行，每行 4 个子查询；数据量大了应改成汇总表/物化视图 |
| 31 | **禁用会员不踢旧 token** | 拦截器只验 JWT；禁用后新登录被拦，旧 token 到期前仍可用（若需实时踢人需在拦截器加状态校验/Redis 黑名单） |
| 32 | **统计口径只看已支付** | `pay_status='PAID'`；已退款（REFUNDED）不计入成交额/销量/趋势 |
| 33 | **品类占比按顶级分类归并** | 商品可能挂在 3 级分类下，SQL 向上 join 最多 3 层（不用递归 CTE） |
| 34 | **商品详情有 Redis 缓存（P8 提前）** | 公开 `catalog/products/{id}` 走 Cache-Aside（key `mall:product:detail:{id}`，TTL 300+[0,120)s）；保存/上下架/删除会删缓存。TTL 内 `stock/sales/rating` 可能是旧值（≤~7min）—— 加购/下单以 DB 为准，评分展示走不缓存的 `/review-stats` |
| 35 | **后台商品详情不吃缓存** | `/api/mall/admin/products/{id}` → `detail()` 直查 DB；只有公开目录走 `detailCached()`。改 VO 字段名时旧缓存 JSON 会解析失败，需先清 `mall:product:detail:*` |

## 9. 部署

一套 `docker-compose.yml` 拉起 **MySQL + Redis + RabbitMQ + 两个后端 + Nginx**（单端口：静态资源 + `/api` 按板块反代）。

```bash
cp deploy/.env.example .env          # 填 JASYPT_ENCRYPTOR_PASSWORD
cd frontend && npm run build && cd ..  # 前端产物给 Nginx 托管
docker compose up -d --build
```

- 配置与步骤详见 [`deploy/README.md`](../deploy/README.md)
- Nginx 反代规则：`/api/mall/**` → 电商 8081，`/api/**` → 外卖 8080
- ⚠️ DB / Redis 密码是 jasypt 密文解密得到的，必须与 compose 环境变量一致（默认 `Ming1234` / `mehado`）
