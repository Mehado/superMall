## 1. 通用约定

### 1.1 统一返回体

**所有接口**（包括失败）HTTP 状态码都是 `200`，业务结果放在 body 里：

```json
{ "code": 1, "msg": null, "data": {} }
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `code` | int | `1` = 成功；`0` = 业务失败 |
| `msg` | string \| null | 失败原因，**已是可直接展示给用户的中文**，成功时为 `null` |
| `data` | any \| null | 业务数据，无返回值的接口为 `null` |

失败示例：

```json
{ "code": 0, "msg": "商品库存不足", "data": null }
```

### 1.2 认证方式

JWT，放在**请求头**里。三个端用**三个不同的头名和不同的密钥**，不能混用：

| 端 | 请求头名 | 登录接口 |
| --- | --- | --- |
| 用户端 | `token` | `POST /api/user/login` |
| 商家端 | `merchant-token` | `POST /api/merchant/login` |
| 配送端 | `delivery-token` | `POST /api/delivery/login` |

三个端的登录都要带 **图形验证码**（`captchaKey` + `captchaCode`，先调 `GET /api/auth/captcha`），账号一律是邮箱。

```
token: eyJhbGciOiJIUzI1NiJ9.eyJyb2xlIjoiVVNFUiIsInVzZXJJZCI6MS...
```

### 1.3 HTTP 状态码

| 状态码 | 含义 | 处理方式 |
| --- | --- | --- |
| `200` | 请求已被处理，看 body 的 `code` | —— |
| `401` | 未携带 token / token 无效 / token 过期 | 清除本地 token，跳转登录页 |

除 `401` 外，其余异常（参数校验失败、业务异常、系统异常）都会被全局异常处理器转成 `code: 0` 的返回体。

### 1.4 分页约定

分页接口统一返回 `PageResult`：

```json
{ "code": 1, "msg": null, "data": { "total": 10, "records": [] } }
```

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `page` | 多数为 `1` | 页码，从 1 开始，最小 1 |
| `pageSize` | 商家端 `10`，用户端浏览 `20` | 每页条数，最小 1 |

⚠️ **`GET /api/user/orders` 的 `page` 和 `pageSize` 没有默认值，必须显式传**，否则报错。

### 1.5 幂等令牌（下单与支付必须遵守）

下单和支付都要求**先取令牌再提交**，令牌一次性消费（Redis + Lua 原子校验并删除），用于防重复提交。

**下单**：

```
1. GET  /api/user/orders/token          → 拿到 token（有效期 10 分钟）
2. POST /api/user/orders/submit         → 请求体里带上 token
```

**支付**：

```
1. GET  /api/user/payment/token?orderNumber=xxx   → 拿到 payToken（有效期 5 分钟）
2. POST /api/user/payment/pay                     → 请求体里带上 payToken
```

令牌只能用一次。重复使用会返回 `code: 0`，提示「订单已提交，请勿重复下单」或「支付令牌无效或已过期」。

### 1.6 数据格式

| 类型 | 格式 | 示例 |
| --- | --- | --- |
| 时间（**JSON 请求体 / 响应体**） | `yyyy-MM-dd HH:mm` | `2026-09-16 16:45` |
| 时间（**GET 查询参数**） | `yyyy-MM-dd HH:mm:ss` | `2026-09-16 00:00:00` |
| 金额 | number，两位小数 | `28.00` |
| 状态 / 枚举 | **字符串** | `"PENDING_PAYMENT"` |
| 图片 | 完整 OSS 公网 URL | `https://mehado-java.oss-cn-beijing.aliyuncs.com/supermall/products/beef-noodle.svg` |
| 启用开关 | `1` 启用 / `0` 禁用（业务语义见各字段） | `1` |

⚠️ **两处格式不一样，容易踩坑**：

- JSON 请求体里的 `LocalDateTime` **只能到分钟，带秒会报错**（`msg: "请求体格式错误或为空"`）
- 查询参数里的 `beginTime` / `endTime` **必须带秒**（`@DateTimeFormat` 指定）
- 响应里的时间同样只到分钟（`2026-09-16 16:45`）

```jsonc
// ✅ 正确
{ "estimatedDeliveryTime": "2026-09-16 20:30" }

// ❌ 错误：请求体格式错误
{ "estimatedDeliveryTime": "2026-09-16 20:30:00" }
```

```
✅ GET /api/merchant/orders?beginTime=2026-09-16 00:00:00
```

### 1.7 参数校验

请求体用 `jakarta.validation` 校验，失败时返回第一条错误信息，例如：

```json
{ "code": 0, "msg": "手机号格式不正确", "data": null }
```

常见约束：手机号 `^1[3-9][0-9]{9}$`、数量最小 1、价格最小 0.01。

**账号与密码规则（2026-09-18 起）**：

| 项 | 规则 | 校验注解 |
| --- | --- | --- |
| 账号 `username` | 必须是邮箱，且域名在常用邮箱后缀白名单内 | `@EmailAccount` |
| 密码 `password` | 8-32 位，且同时包含大写字母、小写字母、数字，不含空白 | `@StrongPassword` |
| 图形验证码 | 三个端的登录 + 用户注册都必须带 | `@RequireCaptcha` |

失败示例：

```json
{ "code": 0, "msg": "邮箱格式不正确，请填写完整邮箱，例如 user@qq.com", "data": null }
{ "code": 0, "msg": "暂不支持该邮箱后缀（qq.con），请使用常用邮箱，如 qq.com / 163.com / gmail.com", "data": null }
{ "code": 0, "msg": "密码不达标：长度需 8-32 位、需包含大写字母（8-32 位，需同时包含大写字母、小写字母和数字）", "data": null }
{ "code": 0, "msg": "验证码不正确", "data": null }
```

> ⚠️ 登录也会过 `@StrongPassword` 做一次**格式预检**（产品要求）。
> 这意味着历史上设置的弱密码账号会卡在格式校验上而无法登录；
> 迁移脚本已把演示账号统一改成 `Mall1234`，自定义密码的旧账号需重置密码。
> 若要去掉这个预检，把三个 `*LoginDTO` 上的 `@StrongPassword` 去掉即可。

## 3. 枚举与状态机

### 3.1 业态 `businessType`

平台有两种业态，用整数表示：

| 值 | 含义 | 说明 |
| --- | --- | --- |
| `1` | 外卖食品 | 餐饮类，来自餐饮商家 |
| `2` | 百货商品 | 日用百货类，来自百货商家 |

- **业态的源头是分类**：`category.businessType` 由商家在创建分类时指定（必填）
- **商品的业态由分类派生**：新增/修改商品时，服务端会读取该商品的分类并把业态写入 `product.businessType`，客户端**不要传也不要改**
- 首页商品流、商家端分类列表、商家端商品列表都支持用 `businessType` 筛选
- 传了非 1/2 的值会报 `msg: "业态类型不合法"`

### 3.2 订单主状态 `status`

```
PENDING_PAYMENT  待支付
PAID             待接单（已支付）
MERCHANT_ACCEPTED 备餐中（商家已接单）
WAITING_DELIVERY 待配送（备餐完成，配送单已生成）
DELIVERING       配送中
COMPLETED        已完成
CANCELLED        已取消
```

状态流转：

```
PENDING_PAYMENT ──支付──▶ PAID ──商家接单──▶ MERCHANT_ACCEPTED ──备餐完成──▶ WAITING_DELIVERY
        │                   │                                                      │
        │                   │                                            配送员取餐 │
    用户取消/超时关单      用户取消/商家拒单                                          ▼
        │                   │                                                 DELIVERING
        ▼                   ▼                                                      │
     CANCELLED ◀─────────────┘                                          确认送达    │
                                                                                   ▼
                                                                              COMPLETED
```

- **可取消的状态只有** `PENDING_PAYMENT` 和 `PAID`
- 所有状态流转都由服务端用「条件更新」实现，客户端**不要本地改状态**，操作成功后重新拉取

### 3.3 支付状态 `payStatus`

```
UN_PAID  未支付
PAID     已支付
REFUND   已退款（订单在已支付后被取消/拒单时置为该状态）
```

### 3.4 配送单状态 `status`

```
WAITING     待抢单（已进入抢单池）
ACCEPTED    已接单，待取餐
DELIVERING  配送中
DELIVERED   已送达
```

流转：`WAITING ──抢单──▶ ACCEPTED ──取餐──▶ DELIVERING ──送达──▶ DELIVERED`

订单状态与配送状态是**两套独立状态**，通过订单 id 关联。

## 5. 公开接口（无需认证）

### 5.0 认证辅助（`/api/auth/**`）

#### 获取图形验证码

```
GET /api/auth/captcha
```

响应：

```json
{
  "code": 1,
  "data": {
    "key": "6cdc1e6d36394a0c875abf6036c2a8fd",
    "image": "iVBORw0KGgoAAAANSUhEUgAAAIQAAAAsCAIAAAAr...",
    "ttlSeconds": 120
  }
}
```

- `image` 是 **PNG 的 base64**（不含 `data:` 前缀），前端拼成 `data:image/png;base64,{image}` 即可。
- 答案只存在 Redis（`captcha:{key}`，TTL 同 `ttlSeconds`），**不落库、不进日志、不下发给客户端**。
- **一次性**：无论校验成功与否，服务端校验后会立即删除，所以失败后必须重新获取。
- 校验不区分大小写；字符集排除了 `0 O 1 I L` 等易混字符。
- 服务端开关：`super-mall.captcha.enabled`（默认 `true`）。置 `false` 时三个端的登录/注册都不校验，接口仍可用。

#### 提交订单

```
POST /api/user/orders/submit
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| addressId | Long | 是 | 收货地址 id |
| merchantId | Long | 是 | 只结算该商家的购物车 |
| remark | String | 否 | 备注 |
| estimatedDeliveryTime | DateTime | 否 | 期望送达时间 |
| payMethod | String | 否 | `MOCK` / `WECHAT` / `ALIPAY` |
| token | String | 是 | 来自 `orders/token` |

请求体示例：

```json
{
  "addressId": 1,
  "merchantId": 1,
  "remark": "不要香菜",
  "payMethod": "MOCK",
  "token": "a1b2c3d4e5f6..."
}
```

响应：

```json
{
  "code": 1,
  "msg": null,
  "data": {
    "id": 3,
    "orderNumber": "17895483582799893",
    "orderAmount": 71.00,
    "orderTime": "2026-09-16 16:45"

```

`orderAmount` = 商品金额 + 配送费。


| 参数 | 必填 | 说明 |
| --- | --- | --- |
| page | **是** | 无默认值 |
| pageSize | **是** | 无默认值 |
| status | 否 | 不传则查全部 |

响应 `data` 为 `{ total, records: OrderVO[] }`，按 `orderTime` 倒序，且只返回当前用户的订单。

#### 订单详情

```
GET /api/user/orders/{id}
```

响应 `data` 为 `OrderVO`。查询他人订单会返回 `msg: "订单不存在"`。

#### 取消订单


该接口有防重复提交保护（5 秒）。

## 7. 商家端接口

认证：请求头 `merchant-token`。

> **数据隔离**：分类、商品、订单的 `merchantId` 全部由登录态决定，请求里**不需要也不应该传**。

> ⚠️ **`description` 是纯文本，入库前会剥掉标签**（XSS 清洗：`<script>` 等标签不落库；正常文字一个字符都不动，`满 100 < 200 减 30` 里的 `<` 不会被转义）。

### 7.1 账号与店铺

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/merchant/login` | 登录 |
| GET | `/api/merchant/shop` | 查询店铺信息 |
| PUT | `/api/merchant/shop` | 修改店铺信息（**字段名是 `shopName` / `logo`**，不是 `name` / `image`） |
| GET | `/api/merchant/shop/business` | 查询**商家自助营业状态**：`1` 营业中 / `0` 休息中 |
| PUT | `/api/merchant/shop/business` | 设置商家自助营业状态 |

登录请求/响应：

```json
// 请求（账号为邮箱；captchaKey/captchaCode 必填）
{ "username": "merchant1@163.com", "password": "Mall1234",
  "captchaKey": "6cdc1e6d...", "captchaCode": "MTDH" }

// 响应
{ "code": 1, "msg": null,
  "data": { "id": 1, "username": "merchant1@163.com", "shopName": "老王牛肉面", "token": "eyJ..." } }
```

修改店铺：

```json
{
  "shopName": "老王牛肉面",
  "logo": "https://...",
  "description": "现煮牛肉面，汤浓面劲道",
  "phone": "13900000001",
  "address": "北京市海淀区中关村大街1号",
  "status": 1
}
```

`shopName` 必填；`logo` / `description` / `phone` / `address` 可选；`status`：1 营业 / 0 停业。

> ⚠️ **字段名**：店名是 `shopName`（不是 `name`）、门头图是 `logo`（不是 `image`）。
> 传错名字不会报错，但**静默不生效**（Jackson 忽略未知字段）。
> ⚠️ `logo` 传 `null` 等于「不修改」（Mapper 用 `<if test="logo != null">`），要清空得传 **空串 `""`**。

#### 商家自助营业状态

```
GET /api/merchant/shop/business
```

响应：

```json
{ "code": 1, "msg": null, "data": 1 }
```

`1` = 营业中，`0` = 休息中。未设置过时默认返回 `1`。

```
PUT /api/merchant/shop/business
```

```json
{ "businessStatus": 0 }
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| businessStatus | Integer | 是 | `1` 营业中 / `0` 休息中，**只接受这两个值** |

> ⚠️ 字段名是 **`businessStatus`**，不是 `status`（传 `status` 会因为 `@NotNull` 被拒）。
> 查询接口的返回值是**数字** `1/0`，不是对象。

返回 `data: null`。传其他值报 `msg: "营业状态不合法"`。

> **与平台状态的区别**：
> - `status` 是**平台状态**（1 营业 / 0 停业），停业后用户端不再展示该商家；
> - `businessStatus` 是**商家自己在后台切换的开关**（1 营业中 / 0 休息中），
>   不影响商家是否出现在列表里，由前端标记「休息中」。
> - 读取时以数据库为准，Redis 做 30 分钟缓存（key `merchant:business:{merchantId}`），写入时同步刷新缓存。

## 9. 调用注意事项

### 9.1 必须遵守的流程

1. **下单**：先 `GET /api/user/orders/token`，再 `POST /api/user/orders/submit` 带上 `token`。跳过取令牌会直接失败。
2. **支付**：先 `GET /api/user/payment/token?orderNumber=`，再 `POST /api/user/payment/pay` 带上 `payToken`。
3. **商家备餐完成**：必须调用 `ready`，否则不会生成配送单，配送端抢单池里不会有这单。
4. **配送端操作**：抢单 → 取餐 → 送达，顺序不能颠倒，且只有接单人本人能操作。

### 9.2 容易踩的坑

| 坑 | 说明 |
| --- | --- |
| 请求头用错 | 三个端头名不同（`token` / `merchant-token` / `delivery-token`），用错会 401 |
| 分页参数漏传 | `GET /api/user/orders` 的 `page`、`pageSize` 无默认值，必须传 |
| 少拆一层 data | 所有数据都在 `data` 里，不在 body 根上 |
| 把 `code` 当 HTTP 状态码 | HTTP 恒为 200，必须判断 body 里的 `code === 1` |
| 无规格商品传了 skuId | 无规格商品 `skuId` 传 `0` 或不传；有规格的商品必须传真实 skuId |
| 用商品 id 当规格 id | `skuId` 是 `skuList[].id`，不是 `productId` |
| 用配送单 id 调配送接口 | 配送接口路径里的 `{orderId}` 是**订单 id** |
| 前端自己算金额 | 提交订单只需要 `addressId` + `merchantId`，金额由服务端根据购物车重算 |
| 改了状态却不刷新 | 所有状态流转在服务端完成，操作成功后要重新拉取列表 |
| 有规格商品的库存 | `product.stock` 是基础库存，实际可售数量看所选规格的 `stock` |
| 商品图可能为空 | `image` 可能为 `null`（如百货类商品），要做占位处理，不要直接渲染成碎图 |
| 业态不要自己传 | 商品的 `businessType` 由分类派生，新增/修改商品时不要传，服务端会覆盖 |
| 重复提交 | 下单/支付/取消/接单/备餐/拒单/抢单/取餐/送达都有限流或防重保护，5 秒内重复调用会被拒 |
| 时间带秒 | JSON 请求体的时间**不能带秒**；查询参数的 `beginTime`/`endTime` **必须带秒**，见 1.6 |
| 登录不带验证码 | 三个端的登录 + 用户注册都要 `captchaKey` + `captchaCode`，漏传报「请先获取图形验证码」 |
| 复用同一张验证码 | 验证码是**一次性**的，无论对错都作废，失败后必须重新获取（换 `key`） |
| 登录时传弱密码 | 密码会做强度预检（8-32 位 + 大小写 + 数字），格式不对会直接报「密码不达标」而不是「密码错误」 |
| 账号传用户名 | 账号现在是**邮箱**（如 `user1@qq.com`），且域名需在常用后缀白名单内 |
| 注册后又调登录 | 注册接口**已经返回 token**，再调登录会报「验证码已过期」（验证码已被注册消费） |

### 9.3 错误提示一览（`code: 0` 时的 `msg`）

## 11. 前端对接速查

> 这一节是给写前端的人看的“抄作业”清单。完整字段定义在上面各章。

### 11.1 登录：三步

```
① GET  /api/auth/captcha
   → { key, image, ttlSeconds }          image 是裸 base64（无 data: 前缀）

② 用户输入：邮箱 / 密码 / 验证码
   <img :src="`data:image/png;base64,${image}`" />

③ POST /api/user/login | /api/merchant/login | /api/delivery/login
   { username(邮箱), password, captchaKey: key, captchaCode: 用户输入 }
   → data: { id, username, nickname|shopName|name, token }

④ 后续所有请求带上对应请求头（见 11.2）
```

### 11.2 三端对照表

| 身份 | 登录接口 | 后续请求头 | 建议落地页 |
| --- | --- | --- | --- |
| 用户 | `POST /api/user/login` | `token` | `/user/home` |
| 商家 | `POST /api/merchant/login` | `merchant-token` | `/merchant/dashboard` |
| 骑手 | `POST /api/delivery/login` | `delivery-token` | `/rider/orders` |

> 三套 JWT 用**不同密钥**签名，头名混用一定 401（这是服务端的角色二次校验，不是 bug）。

### 11.3 验证码组件必须注意的 4 件事

1. **一次性**：无论对错，服务端校验后立即作废。
   → **登录失败后必须重新 `GET /api/auth/captcha` 并清空输入框**，否则下次提交报「验证码已过期或已使用」。
2. **大小写不敏感**：用户输入小写也能过；建议输入框做 `text-transform: uppercase` 只为了好看。
3. **有效期**：`ttlSeconds`（默认 120）。建议前端做个倒计时，快过期时提示或自动刷新。
4. **可能被关闭**：`GET /api/auth/policy` 的 `captchaRequired === false` 时，**不要渲染验证码控件，也不要传这两个字段**。
   （服务端置 `false` 时即使传了也不校验，但隐藏控件体验更好）

### 11.4 规则不要写死在前端

```
GET /api/auth/policy
→ { emailDomains: [...40 个后缀], emailExample, passwordDesc,
    passwordMin: 8, passwordMax: 32, captchaRequired: true }
```

| 用途 | 做法 |
| --- | --- |
| 邮箱后缀补全 / 快选 | 直接用 `emailDomains` 渲染按钮，不要在前端再写一份 |
| 密码强度提示文案 | 用 `passwordDesc`；逐条勾选用 `passwordMin/Max` |
| 是否需要验证码 | 用 `captchaRequired` |

> 建议：拉一次缓存在前端 store，同时保留一份内置兑底清单 —— 接口挂了不能让登录页不能使用。

### 11.5 注册（仅用户端）

```
POST /api/user/register
```

```json
// 请求
{
  "username": "newuser@qq.com",
  "password": "Mall1234",
  "nickname": "小明",
  "phone": "13800000001",
  "captchaKey": "6cdc1e6d...",
  "captchaCode": "MTDH"
}

// 响应：★ 直接返回 token，不是 null
{
  "code": 1,
  "data": { "id": 4, "username": "newuser@qq.com", "nickname": "小明", "token": "eyJhbGciOiJIUzI1NiJ9..." }
```

> ⚠️ **拿到 token 就算登录完成，不要再调一次登录接口** —— 验证码已被注册消费，

### 11.6 统一错误处理

```js
// 响应拦截器骨架
const body = res.data
if (body.code === 1) return body.data      // 成功：取 data
notify(body.msg)                            // 失败：msg 直接展示给用户
return Promise.reject(new Error(body.msg))

// HTTP 401（错误分支里）
if (err.response?.status === 401) {
  clearToken()                              // 登录已过期 / 未登录
  router.replace('/login')
}
```

| 项 | 说明 |
| --- | --- |
| HTTP 状态码 | 业务失败也是 **200**，必须判断 body 的 `code` |
| 错误文案 | `msg` 已经是一句可直接展示的中文（如「验证码不正确」），不用自己再映射 |
| 401 | 未登录 / token 过期 / 请求头用错（头名与身份不匹配） |

### 11.7 字段级校验错误文案（前端可直接复用）

| 场景 | `msg` |
| --- | --- |
| 邮箱为空 | 邮箱不能为空 |
| 邮箱缺 `@` | 请填写完整邮箱，例如 user@qq.com |
| 邮箱格式错 | 邮箱格式不正确，请填写完整邮箱，例如 user@qq.com |
| 后缀不在白名单 | 暂不支持该邮箱后缀（qq.con），请使用常用邮箱，如 qq.com / 163.com / gmail.com |
| 密码为空 | 密码不能为空 |
| 密码不达标 | 密码不达标：长度需 8-32 位、需包含大写字母（8-32 位，需同时包含大写字母、小写字母和数字） |
| 验证码未填 | 请填写图形验证码（前端拦）/ 请先获取图形验证码（后端拦，说明没传 key） |
| 验证码错 | 验证码不正确 |
| 验证码过期 | 验证码已过期或已使用，请点击图片刷新 |
| 邮箱已注册 | 该邮箱已被注册 |

## 12. 平台运营与入驻（2026-09-22 新增）

外卖从「种子商家」升级为**真正的多商家平台**：新增**平台运营**角色，负责
**审核商家入驻**与**管理骑手**；商家、骑手都可以自助注册。

> 之前 `merchant` / `deliveryman` 只能靠 SQL 插库，平台方没有任何入口。
> 现在链路是：**商家提交入驻申请 → 平台审核（通过 / 驳回）→ 通过后才可登录经营**；
> 骑手注册即启用，平台可停用异常账号。

### 12.1 角色与请求头

| 角色 | 请求头 | 登录接口 | 演示账号 |
| --- | --- | --- | --- |
| 平台运营 | `platform-token` | `POST /api/platform/login` | `platform@163.com` / `Admin1234` |
| 商家 | `merchant-token` | `POST /api/merchant/login` | 自助入驻或种子账号 |
| 骑手 | `delivery-token` | `POST /api/delivery/login` | 自助注册或种子账号 |

> ⚠️ 平台运营使用**独立密钥 + 独立请求头**，与商家 / 骑手 / 买家 token **互不通用**：
> 拿商家 token 打 `/api/platform/**`、或拿 `platform-token` 打 `/api/merchant/**`，都会 **401**。

### 12.2 商家入驻

#### 提交入驻申请（公开）

```
POST /api/merchant/apply
```

```json
{
  "username": "newshop@163.com",
  "password": "Mall1234",
  "shopName": "川味小馆",
  "contactName": "张三",
  "phone": "13900000099",
  "address": "北京市朝阳区望京街 9 号",
  "description": "主打川菜",
  "licenseImage": "https://.../license.png",
  "captchaKey": "6cdc1e6d...",
  "captchaCode": "MTDH"
}
```

- 落库为 `auditStatus=0`（待审核）、`status=0`（未营业）；**不返回 token**（未过审不能登录）。
- `username`（邮箱）、`password`（强度）、`shopName`、`contactName`、`phone`、`address` 必填。
- 邮箱已存在时：**待审核 / 已通过** → 报「该邮箱已提交过入驻申请」；
  **已驳回** → 允许用同一邮箱**重新提交**（复用同一行，重新置为待审核）。

响应：

```json
{ "code": 1, "msg": null,
  "data": { "id": 4, "username": "newshop@163.com", "shopName": "川味小馆",
            "auditStatus": 0, "auditStatusDesc": "待审核",
            "rejectReason": null, "message": "入驻申请已提交，请等待平台审核" } }
```

#### 查询申请状态（公开）

```
GET /api/merchant/apply/status?username=newshop@163.com
```

返回同上结构；`auditStatusDesc` 为 `待审核 / 已通过 / 已驳回`，被驳回时带 `rejectReason`。

#### 商家登录的审核门禁

`POST /api/merchant/login` 在密码正确后先判审核状态：

| auditStatus | 登录结果 |
| --- | --- |
| 0 待审核 | 拒绝：`店铺入驻申请审核中，请耐心等待平台审核` |
| 2 已驳回 | 拒绝：`店铺入驻申请未通过：<驳回原因>` |
| 1 已通过 | 继续判营业状态，通过则签发 `merchant-token` |

> 历史/种子商家的 `audit_status` 默认是 `1`，不受影响。

### 12.3 平台运营

认证：请求头 `platform-token`。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/platform/login` | 登录（需验证码），返回 `token` |
| GET | `/api/platform/profile` | 查自己的资料（`password` 恒为 `null`） |
| PUT | `/api/platform/profile` | 改自己的资料（目前只有 `name`） |
| GET | `/api/platform/overview` | 看板：待审商家 / 已通过 / 已驳回 / 骑手数 |
| GET | `/api/platform/merchants/page` | 入驻申请分页（`auditStatus` / `keyword` / `page` / `pageSize`） |
| PUT | `/api/platform/merchants/{id}/audit` | 审核（`{ approved, reason }`） |
| GET | `/api/platform/deliverymen/page` | 骑手分页（`keyword` / `status`） |
| PUT | `/api/platform/deliverymen/{id}/status` | 启用 / 停用骑手（`status=1\|0`） |

审核请求：

```json
// 通过
{ "approved": true }
// 驳回（reason 必填）
{ "approved": false, "reason": "营业执照照片不清晰，请重新上传" }
```

- 审核用**条件更新**（`where audit_status = 0`）：并发 / 重复审核只会成功一次，
  重复审核报「该入驻申请已审核过，不能重复审核」。

改自己的资料：

```json
// PUT /api/platform/profile
{ "name": "平台运营" }
```

| 字段 | 必填 | 约束 |
| --- | --- | --- |
| name | 是 | 非空，最长 50 字 |

> `platform_admin` 表只有 账号 / 密码 / 状态 / 姓名，所以可改字段只有 `name`；
> 登录账号（邮箱）与状态不可自改。
- 通过 → `audit_status=1`、`status=1`（店铺可直接营业）；驳回 → `audit_status=2`、`status=0`。

### 12.4 骑手注册

```

```

```json
{ "username": "rider3@gmail.com", "password": "Mall1234",
```
