# 在线外卖商城项目大纲

## 一、项目定位

一个支持**多商家、多用户、配送员**的在线外卖商城。

采用前后端分离架构：

```text
                    ┌──────────────┐
                    │   Vue3 用户端 │
                    └──────┬───────┘
                           │
                    ┌──────▼───────┐
                    │              │
                    │ Spring Boot  │
                    │    后端      │
                    │              │
                    └──┬────┬───┬──┘
                       │    │   │
             ┌─────────┘    │   └─────────┐
             ▼              ▼             ▼
          MySQL           Redis       RabbitMQ
```

三个 Web 端：

- 用户端：Vue3
- 商家端：Vue3
- 配送员端：Vue3

后端统一使用 Spring Boot。

---

## 二、系统角色

### 1. 用户

负责：

- 注册 / 登录
- 浏览商家
- 浏览商品
- 加入购物车
- 提交订单
- 支付
- 查看订单
- 取消订单
- 查看配送状态
- 管理收货地址

### 2. 商家

**一个商家对应一个账号**，不设计商家内部员工、子角色和复杂 RBAC。

负责：

- 登录
- 店铺管理
- 分类管理
- 商品管理
- 库存管理
- 查看订单
- 接单
- 完成备餐

### 3. 配送员

平台级配送员，不属于某个固定商家。

负责：

- 登录
- 查看待配送订单
- 抢单
- 查看配送订单
- 开始配送
- 确认送达

## 四、数据库设计

核心表：

```text

category              商品分类
product               商品
sku                   商品规格

address               收货地址

cart                  购物车
cart_item             购物车明细

orders                订单
order_item            订单明细

delivery_order        配送单
```

关系：

```text
sys_user
 ├── merchant
 ├── deliveryman
 ├── address
 └── cart
       └── cart_item

merchant
 ├── category
 └── product
       └── sku

orders
 ├── order_item
 └── delivery_order
        └── deliveryman
```

### 多商家数据隔离

所有商家自己的核心业务数据都带 `merchant_id`：

- category.merchant_id
- product.merchant_id
- orders.merchant_id
- 其他后续商家业务数据

这样可以实现：

```text
商家 A → 只能查询和操作自己的商品、订单

商家 B → 只能查询和操作自己的商品、订单
```

不引入复杂的商家 RBAC。

## 五、订单状态设计

订单主状态：

```text
PENDING_PAYMENT
      │
      ▼
PAID
      │
      ▼
MERCHANT_ACCEPTED
      │
      ▼
WAITING_DELIVERY
      │
      ▼
DELIVERING
      │
      ▼
COMPLETED
```

异常状态：

```text
PENDING_PAYMENT ──→ CANCELLED

PAID ──→ CANCELLED
```

配送单单独维护状态：

```text
WAITING
   ↓
ACCEPTED
   ↓
DELIVERING
   ↓
DELIVERED
```

原则：

> 订单状态和配送状态分离。

## 八、Redis 使用场景

Redis 不为了使用而使用，而是针对实际业务问题。

### 1. 商品缓存

```text
查询商品
 ↓
Redis
 ↓
缓存不存在
 ↓
MySQL
 ↓
写入 Redis
```

学习：

- Cache Aside
- 缓存穿透
- 缓存击穿
- 缓存雪崩

### 2. 库存扣减

例如：

```text
商品库存：100
       ↓
100 个用户同时下单
       ↓
Redis + Lua
       ↓
原子扣减库存
```

避免超卖。

### 3. 配送员抢单

```text
订单 #10001
       ↓
     待抢单
       ↓
配送员 A ─┐
配送员 B ─┼──→ 同时抢单
配送员 C ─┘
       ↓
只有一个成功
```

使用 Redis + Lua 保证抢单操作的原子性。

### 4. 防重复提交

例如用户短时间内连续点击：

```text
立即支付
立即支付
立即支付
```

使用 Redis `SETNX` 控制短时间重复请求。

## 九、RabbitMQ 使用场景

### 1. 支付成功后的异步处理

```text
支付成功
   ↓
RabbitMQ
   ↓
异步处理订单相关业务
```

### 2. 订单超时取消

```text
订单创建
 ↓
15 分钟未支付
 ↓
延迟消息
 ↓
自动取消
 ↓
恢复库存
```

### 3. 异步统计

```text
订单完成
 ↓
RabbitMQ
 ↓
异步更新销量 / 统计数据
```

原则：

> 先有业务问题，再引入 RabbitMQ，而不是为了展示技术栈强行使用 MQ。

## 十六、核心设计原则

### 原则 1：先业务，后技术

不要为了使用 Redis、RabbitMQ 而强行加入。

应该：

```text
业务问题
   ↓
分析原因
   ↓
寻找解决方案
   ↓
引入技术
```

### 原则 2：先简单实现，再解决复杂问题

先让：

```text
用户 → 下单 → 商家接单 → 配送 → 完成
```

完整跑通。

再逐步增加：

```text
Redis
MQ
并发
幂等
缓存
```

### 原则 3：理解每一层为什么存在

开发过程中不仅关注：

```text
“代码怎么写”
```

还要理解：

```text
为什么这样设计？
为什么这个数据放 MySQL？
为什么这里需要 Redis？
为什么这里需要 MQ？
为什么需要事务？
为什么需要幂等？
```

### 原则 4：以能够独立复现为最终目标

这个项目的最终目标不是让 Agent 帮忙生成一个项目，而是能够自己解释并实现：

```text
数据库设计
        ↓
接口设计
        ↓
Service 业务逻辑
        ↓
事务
        ↓
Redis
        ↓
RabbitMQ
        ↓
并发控制
        ↓
部署
```
