# superMall 外卖前端开发手册

> 这是**外卖端前端**的「照着做」手册：三大角色（用户/商家/骑手）每个页面调哪些接口、按什么顺序调、坑在哪。
> 逐字段的完整契约在 [`外卖接口文档.md`](外卖接口文档.md)（**67 个端点**，含「11. 前端对接速查」），本文只给结构与调用姿势。
>
> 📌 **外卖前端已经存在**：`frontend`（单工程三端合一，即 `http://localhost` 现在跑的那套）。
> 本文既可用于**维护/改造现有前端**，也可用于照着它重写。电商板块看 [`电商前端开发手册.md`](电商前端开发手册.md)。

## 0. 先知道后端边界

| 能做 | 说明 |
| --- | --- |
| 认证 | 三端独立 JWT（用户/商家/骑手），图形验证码 + 邮箱账号 + 密码强度校验 |
| 用户端 | 浏览商家/商品、购物车、收货地址、下单、Mock 支付、订单查询/取消 |
| 商家端 | 登录、店铺信息、自助营业状态、分类 CRUD、商品 CRUD + SKU、订单接单/备餐/拒单、图片上传、订单统计 |
| 骑手端 | 登录、资料、抢单池、抢单、我的配送、取餐、送达、统计 |
| 公开 | 首页随机商品流（支持业态筛选）、商家列表/详情、分类、店内商品分页、商品详情 |
| 异步 | 下单 15 分钟未支付自动关单（MQ + 定时任务双保险） |

| **不要做** | 说明 |
| --- | --- |
| 真实支付 | 只有 Mock 支付（点一下即成功） |
| WebSocket 实时推送 | 后端 `WebSocketServer` 有推送能力，但**现有前端未接入**，仍靠轮询（商家 30s、骑手 15s） |
| 优惠券 / 会员体系 | 外卖侧没有这些概念 |

**两种业态**（`businessType`）：`1` 外卖食品 / `2` 百货商品。业态的源头是**分类**，商品的业态由分类派生（前端不要传）。

## 1. 五分钟接通后端

### 1.1 请求地址
前端 `axios` 的 `baseURL` **留空**，用相对路径 `/api/...`：

| 跑法 | 谁转发 `/api`、`/img` |
| --- | --- |
| `npm run dev`（Vite :5173） | `vite.config.js` 的 `server.proxy` → `http://localhost:8080` |
| Nginx（:80，当前本机） | `/api/**`、`/img/**` → `8080` |

### 1.2 统一返回体
```json
{ "code": 1, "msg": null, "data": { } }
```
- `code === 1` 成功取 `data`；`code === 0` 弹 `msg`
- **HTTP 恒为 200**（业务失败也是 200）；401 = 未登录/token 失效
- 分页统一 `{ total, records: [...] }`

### 1.3 鉴权：三把 token，三个头名
| 身份 | 登录接口 | 后续请求头 | 建议落地页 |
| --- | --- | --- | --- |
| 用户 | `POST /api/user/login` | `token` | `/user/home` |
| 商家 | `POST /api/merchant/login` | `merchant-token` | `/merchant/dashboard` |
| 骑手 | `POST /api/delivery/login` | `delivery-token` | `/rider/orders` |

> 三套 JWT 用**不同密钥**签名，头名混用一定 401（这是角色二次校验，不是 bug）。
> 现有实现见 `frontend/src/utils/request.js`（按 `localStorage` 里的 `role` 自动选头）。

### 1.4 图形验证码（三端登录 + 用户注册都要）
```
GET /api/auth/captcha   → { key, image(PNG base64), ttlSeconds }
```
```html
<img :src="`data:image/png;base64,${image}`" />
```
- **一次性**：无论对错都作废 → **登录失败后必须重新拉一张**
- 先调 `GET /api/auth/policy` 拿账号规则 / 密码规则 / `captchaRequired`（`false` 时不渲染验证码控件）
- 提交时字段名是 `captchaKey` + `captchaCode`

### 1.5 登录三步（三端一样）
```js
1) GET  /api/auth/policy                     // 规则（可缓存）
2) GET  /api/auth/captcha                    // { key, image }
3) POST /api/<user|merchant|delivery>/login  // { username, password, captchaKey, captchaCode }
```
- 账号是**邮箱**（`user1@qq.com`），域名需在常用后缀白名单内
- 登录会**预检密码强度**（8-32 位 + 大小写 + 数字），格式不对直接报「密码不达标」

## 3. 用户端：页面 → 接口（头 `token`）

### 3.1 首页 / 商家列表

> **字标后面的横向滚动图片墙**：`components/FlowingGallery.vue`，图池 `frontend/photo/marquee-food/`。
> 2 行横向跑马灯、5 张一组、无限循环；三层动效：轨道循环 + 卡片 4.4s 错峰待机浮动 + 鼠标 3D 倾斜/图片视差。
> 层级：图片 1 → 白柔光 2 → 字标 3 → 搜索框 4 —— **图片在字标后面，不会盖住字**，也不挡搜索框。
> 与商城首页（`MallHomeView`）同构，**改一页记得同步另一页**。
> 改图只需往 `photo/marquee-food/` 丢图（文件名随意，01、02… 控顺序；**真实格式要和扩展名一致**）。

| 模块 | 接口 |
| --- | --- |
| 首页随机商品流（可按业态） | `GET /api/public/products?businessType=1&keyword=&limit=6` → 返回**列表**（随机抽取，不是分页） |
| 商家列表 | `GET /api/public/merchants` |
| 商家详情 | `GET /api/public/merchants/{id}` |
| 店内分类 | `GET /api/public/merchants/{id}/categories` |
| 店内商品分页 | `GET /api/public/merchants/{id}/products?page=1&pageSize=10&categoryId=&businessType=&name=` |
| 商品详情（带缓存） | `GET /api/public/products/{id}` |

> `/api/public/**` **无需登录**，游客可浏览。

### 3.2 购物车（按「用户 × 商家」隔离）
| 操作 | 接口 |
| --- | --- |
| 查询（按商家分组） | `GET /api/user/cart` → `CartVO[]` |
| 加入 | `POST /api/user/cart` body `{ merchantId, productId, skuId, number }` |
| 改数量 | `PUT /api/user/cart` body `{ id, number }`（**`number=0` 即删除**） |
| 删单条 | `DELETE /api/user/cart/{id}` |
| 清空某商家 | `DELETE /api/user/cart/merchant/{merchantId}` |
| 清空全部 | `DELETE /api/user/cart` |

- ⚠️ **无规格商品 `skuId` 传 `0` 或不传**；有规格必须传真实 `skuId`（`skuList[].id`）
- 同商家「同商品 + 同规格」会**累加数量**，不新增行
- `{id}` 是**购物车明细 id**（`CartVO.items[].id`），不是商品 id

### 3.3 收货地址
| 操作 | 接口 |
| --- | --- |
| 列表 | `GET /api/user/address` |
| 详情 | `GET /api/user/address/{id}` |
| 新增 | `POST /api/user/address` |
| 修改 | `PUT /api/user/address`（body 带 `id`） |
| 删除 | `DELETE /api/user/address/{id}` |
| 设为默认 | `PUT /api/user/address/default/{id}` |

> 外卖地址是**纯文本省市区**（没有电商那套 `areaCode` 三级联动）；第一条自动默认。

### 3.4 下单 → 支付（**两步各一次令牌**）
```
1) GET  /api/user/orders/token                 → data 为令牌字符串（10 分钟、一次性；IP 限流 30/分钟）
2) POST /api/user/orders/submit
   body { addressId, merchantId, remark?, estimatedDeliveryTime?, payMethod?, token }
   → { id, orderNumber, orderAmount, orderTime }
3) GET  /api/user/payment/token?orderNumber=xxx → data 为支付令牌（5 分钟、一次性）
4) POST /api/user/payment/pay
   body { orderNumber, payToken }
```
- **只结算该商家**的购物车（外卖按商家拆单）
- 金额由服务端根据购物车重算 + 配送费，**前端只传地址和商家**
- 成功后服务端**清空该商家购物车**，并投递 15 分钟延迟关单消息
- 令牌一次性，跳过取令牌会直接失败

### 3.5 我的订单
| 操作 | 接口 |
| --- | --- |
| 分页 | `GET /api/user/orders?page=1&pageSize=10&status=DELIVERING` |
| 详情 | `GET /api/user/orders/{id}` |
| 取消 | `PUT /api/user/orders/cancel/{id}`（仅 `PENDING_PAYMENT` / `PAID`） |

- ⚠️ **`page` / `pageSize` 没有默认值，必须传**（不传 400）
- 这里的 `{id}` 是**订单 id**
- 取消后已支付的会置 `payStatus=REFUND` 并回补库存

### 3.6 我的 / 个人中心
| 模块 | 接口 |
| --- | --- |
| 资料 | `GET /api/user/profile`（含 `avatar`，没设置过为 `null`） |
| 改资料 | `PUT /api/user/profile`（可只传想改的字段：`nickname` / `phone` / `avatar`） |
| **上传头像** | `POST /api/user/avatar`（multipart 字段名 `file`，≤2MB 图片）→ 返回 OSS URL |
| 改密码 | `PUT /api/user/password` |
| 注册 | `POST /api/user/register`（**直接返回 token**，不要再登录） |

**头像两步走**（与商家传图同理，库里只存 URL）：

```
① POST /api/user/avatar            （file=图片）→ data = OSS URL
② PUT  /api/user/profile           { "avatar": "<上一步的 URL>" }
   清除头像：{ "avatar": "" }
```

> 前端已封装：`foodUserApi.uploadAvatar(file)` + `foodUserApi.updateProfile({ avatar })`，
> 组件用 `components/AvatarUploader.vue`（点圆形头像即选图，自动走完两步）。
> 头像会同步到左侧导航栏（`NavRail` 的 `accountAvatar`）。
> ⚠️ **登录邮箱不可改**：`PUT /api/user/profile` 没有 `email` 字段。

## 4. 商家端：页面 → 接口（头 `merchant-token`）

| 页面 | 接口 |
| --- | --- |
| 登录 | `POST /api/merchant/login` |
| 店铺信息 | `GET /api/merchant/shop`；`PUT /api/merchant/shop` |
| 营业状态开关 | `GET /api/merchant/shop/business`（返回**数字** 1/0）；`PUT /api/merchant/shop/business` body `{ businessStatus }` |
| 分类管理 | `GET /api/merchant/categories`（可按 `businessType` 筛）；`GET /{id}`；`POST`；`PUT`；`DELETE /{id}` |
| 商品列表 | `GET /api/merchant/products?page=1&pageSize=10&name=&categoryId=&businessType=&status=` |
| 商品详情 | `GET /api/merchant/products/{id}` |
| 商品新增/修改 | `POST` / `PUT /api/merchant/products` |
| 商品删除 | `DELETE /api/merchant/products/{id}` |
| 规格查询 | `GET /api/merchant/skus/product/{productId}`；`GET /api/merchant/skus/{id}` |
| 图片上传 | `POST /api/merchant/file/upload`（multipart 字段 `file`） |
| 订单看板 | `GET /api/merchant/orders?page=&pageSize=&status=&number=&phone=&beginTime=&endTime=` |
| 订单统计 | `GET /api/merchant/orders/statistics` |
| 订单详情 | `GET /api/merchant/orders/{id}` |
| 接单 | `PUT /api/merchant/orders/accept/{id}`（`PAID` → `MERCHANT_ACCEPTED`） |
| 备餐完成 | `PUT /api/merchant/orders/ready/{id}`（→ `WAITING_DELIVERY`，**自动生成配送单进入抢单池**） |
| 拒单 | `PUT /api/merchant/orders/reject` body `{ id, cancelReason }`（`PAID` → `CANCELLED` + 退款 + 回补库存） |
| 模拟支付（调试） | `PUT /api/merchant/orders/simulate-pay/{orderNumber}` |

- **备餐完成必须调 `ready`**，否则不会生成配送单，骑手抢单池里看不到
- 订单列表查询参数：`beginTime` / `endTime` 格式 **`yyyy-MM-dd HH:mm:ss`（必须带秒）**
- **休息中**（营业状态关闭）服务端会强制禁止用户加购与下单

**店铺设置的两个坑（都已修，写新代码别再踩）**：

| 坑 | 正确写法 |
| --- | --- |
| 店名 / 门头图字段名 | `PUT /api/merchant/shop` 用 **`shopName`** 和 **`logo`**；传 `name` / `image` 会被 Jackson 静默忽略（不报错但不生效） |
| 营业状态字段名 | `PUT /api/merchant/shop/business` 用 **`businessStatus`**（不是 `status`），否则 `@NotNull` 直接拒；`GET` 返回的是数字，不是对象 |

> `merchant` 表只有 店名/logo/简介/电话/地址（+ 平台状态、审核字段），
> 所以「业态 / 配送费 / 起送价 / 营业时间」这些输入框**没有后端字段**，页面已移除。
> 配送费目前是全局配置 `super-mall.delivery.base-fee`，不是每店可调。

## 5. 骑手端：页面 → 接口（头 `delivery-token`）

| 页面 | 接口 |
| --- | --- |
| 登录 | `POST /api/delivery/login` |
| 资料 | `GET /api/delivery/profile`；`PUT /api/delivery/profile`（**只有 `name` / `phone`** 可改，和买家共用 `ProfileEditModal`） |
| 抢单池 | `GET /api/delivery/orders/pool?page=1&pageSize=10` |
| 抢单 | `PUT /api/delivery/orders/grab/{orderId}` |
| 我的配送 | `GET /api/delivery/orders/mine?page=&pageSize=&status=` |
| 配送单详情 | `GET /api/delivery/orders/{orderId}` |
| 取餐 | `PUT /api/delivery/orders/pickup/{orderId}`（`ACCEPTED` → `DELIVERING`，订单也变 `DELIVERING`） |
| 送达 | `PUT /api/delivery/orders/delivered/{orderId}`（→ `DELIVERED`，订单 `COMPLETED`，异步累加销量） |
| 配送统计 | `GET /api/delivery/orders/statistics` |

- ⚠️ **路径里的 `{orderId}` 是订单 id**（`DeliveryOrderVO.orderId`），**不是配送单 id**（`id`）
- 抢单是并发安全的：同一单只会有一个骑手抢到；失败提示「手慢了，配送单已被抢走」→ 刷新列表即可
- 取餐/送达只有**接单人本人**能操作（否则「无权操作该配送单」）

## 6. 状态机与按钮映射

### 6.1 订单主状态
```
待支付 PENDING_PAYMENT ─支付→ 待接单 PAID ─接单→ 备餐中 MERCHANT_ACCEPTED ─备餐完成→ 待配送 WAITING_DELIVERY
        │                      │                                                              │ 取餐
   用户取消/超时           用户取消/商家拒单                                                 ▼
        ▼                      ▼                                                          配送中 DELIVERING
     已取消 CANCELLED ◀─────────┘                                                              │ 送达
                                                                                                ▼
                                                                                          已完成 COMPLETED
```

| 订单 `status` | 用户端按钮 | 商家端按钮 |
| --- | --- | --- |
| `PENDING_PAYMENT` | 去支付 / 取消订单 | —— |
| `PAID` | 取消订单 | **接单** / 拒单 | 
| `MERCHANT_ACCEPTED` | —— | **备餐完成** |
| `WAITING_DELIVERY` / `DELIVERING` | 查看进度 | —— |
| `COMPLETED` | 再来一单 | —— |
| `CANCELLED` | —— | —— |

### 6.2 配送单状态（与订单状态**两套独立**，靠订单 id 关联）
```
WAITING ──抢单──▶ ACCEPTED ──取餐──▶ DELIVERING ──送达──▶ DELIVERED
```
| 配送单 `status` | 骑手端按钮 |
| --- | --- |
| `WAITING`（在抢单池） | **抢单** |
| `ACCEPTED` | **取餐** |
| `DELIVERING` | **确认送达** |
| `DELIVERED` | —— |

> 所有状态流转都在服务端完成，**客户端不要本地改状态**，操作成功后重新拉取。

## 7. 一次完整链路的调用顺序（联调照着走）

```
用户   登录 → 浏览商家/商品 → 加购（POST /api/user/cart）
用户   取下单令牌 → 提交订单（POST /api/user/orders/submit）
用户   取支付令牌 → 支付（POST /api/user/payment/pay）
商家   登录 → 订单看板看到 PAID → 接单 accept → 备餐完成 ready（生成配送单）
骑手   登录 → 抢单池看到 WAITING → 抢单 grab → 取餐 pickup → 送达 delivered
用户   订单详情看到 COMPLETED；商家/骑手统计数字 +1
```

## 8. 数据模型速查（关键字段）

| 模型 | 关键字段 | 说明 |
| --- | --- | --- |
| `Product` / `ProductVO` | `id, name, image, price, stock, businessType, merchantId, skuList` | `image` 可能为 null；有规格时实际库存看所选 SKU 的 `stock` |
| `Sku` | `id, productId, name, price, stock` | `skuId` 是它，不是 `productId` |
| `CartVO` | `merchantId, shopName, items[]` | 按商家分组；`items[].id` 是购物车明细 id |
| `OrderVO` | `id, number, status, payStatus, amount, deliveryFee, orderItems[], consignee, phone, address, orderTime` | `number` 是订单号，`id` 是订单 id |
| `DeliveryOrderVO` | `id, orderId, status, shopName, pickupAddress, receiverAddress, consignee, phone, deliveryFee` | `orderId` 才是调配送接口用的 id |
| `Address` | `id, consignee, phone, province, city, district, detail, isDefault` | 外卖是文本省市区 |

> 完整字段表见 [`外卖接口文档.md`](外卖接口文档.md) 第 2 章。

## 9. 前端最容易踩的坑

| # | 坑 | 正确做法 |
| --- | --- | --- |
| 1 | 三个请求头用错 | `token` / `merchant-token` / `delivery-token` 严格对应角色 |
| 2 | `page`/`pageSize` 不传 | `GET /api/user/orders` 无默认值，**必传** |
| 3 | 把 `code` 当 HTTP 状态 | HTTP 恒 200，判 `code === 1` |
| 4 | 无规格商品传了 skuId | 传 `0` 或不传；有规格必须传真实 `skuId` |
| 5 | 把 `productId` 当 `skuId` | `skuId` 取 `skuList[].id` |
| 6 | 配送接口用了配送单 id | 路径 `{orderId}` 是**订单 id** |
| 7 | 前端自己算金额 | 只传 `addressId` + `merchantId`，金额服务端重算 |
| 8 | 改了状态不刷新 | 状态在服务端流转，操作后重新拉列表 |
| 9 | 时间格式 | JSON 请求体时间**不能带秒**；查询参数 `beginTime/endTime` **必须带秒** |
| 10 | 验证码复用 | 一次性，登录失败要重新拉；`captchaRequired=false` 时不渲染 |
| 11 | 注册后又调登录 | 注册接口**直接返回 token** |
| 12 | 账号写成用户名 | 现在是**邮箱**，且有后缀白名单 |
| 13 | 商品图不占位 | 百货商品 `image` 为 `null`，必须占位 |
| 14 | 业态自己传 | `businessType` 由分类派生，前端不传 |
| 15 | 5 秒内重复点 | 下单/支付/取消/接单/备餐/拒单/抢单/取餐/送达都有防重，重复调会被拒 |
| 16 | 商家没点「备餐完成」就等骑手 | 必须先 `ready` 才生成配送单 |
| 17 | **登录后无条件跟着 `redirect` 跳** | 六端会话按角色隔离（一角色一把 token）。在 A 端被拦下（`redirect=/shop/me`）后到登录页，又把身份切成 B 端再登录 —— 再按 redirect 跳 A 的页面会被守卫拦回登录页，表现为「提示登录成功却卡住」。规则：`redirect` 属于公开页或刚登录的身份才用，否则回该身份主页（`frontend/src/router/index.js` 的 `landingFor()`） |
| 18 | **富文本别指望原样存** | 商品详情是**富文本**，入库前会 XSS 清洗（白名单：`p/br/strong/em/u/ul/ol/li/h1-h4/blockquote/hr/code/pre` + `a[href]`/`img[src]`）；评价内容 / 退款说明 / 店铺简介这类**纯文本**字段会剥标签。`script`、`on*` 事件、`javascript:`/`data:` 地址不落库，站内相对图片地址（`/seed/...`）保留 |

### 13.1 角色与请求头（多了一把 token）

### 13.2 页面 → 接口

| 页面 | 路由 | 接口 | 说明 |
| --- | --- | --- | --- |
| 商家入驻申请 | `/merchant/apply`（公开） | `POST /api/merchant/apply`、`GET /api/merchant/apply/status` | 提交后待审核；被驳回可同邮箱重提 |
| 骑手注册 | `/rider/register`（公开） | `POST /api/delivery/register` | 注册即启用，响应直接带 `token`（注册即登录） |

`platformApi.*`。

### 13.3 三个必须知道的点

1. **平台运营登录没有 `/profile`** —— 登录响应本身就是资料（`id / username / name / token`），
   `LoginView.submit` 对平台角色直接把响应当 profile 存。
2. **入驻不返回 token** —— 没通过审核不能登录商家端，所以入驻页只显示状态，不自动登录。
   骑手注册相反：直接返回 token、直接跳 `/rider`。
3. **token 互不通用** —— `platform-token` 打 `/api/merchant/**`、`merchant-token` 打 `/api/platform/**` 都是 401。
   请求实例已经按角色隔离，正常调用不会踩到。
